## 1. 项目目标

实现一个**简化版的在线问卷系统**（功能对标问卷星 / Google Forms），重点考察以下能力：


| 目标维度             | 落地形式                                                       |
| ---------------- | ---------------------------------------------------------- |
| MongoDB 数据库设计能力  | 5 个独立集合，`validation` / `next_rule` 入库而非写死                  |
| 后端程序设计能力         | FastAPI + Repository 层 + 解释器引擎                             |
| 数据结构与业务逻辑建模能力    | 半结构化文档建模，题型差异通过文档字段表达                                      |
| 条件逻辑与跳转实现        | `by_option` / `by_contains` / `by_range` / `default` 四种解释器 |
| 使用 AI 编程工具的能力与规范 | 全程 AI 协作，过程完整记录于 `AI使用过程.md`                               |


> 本阶段不追求复杂界面，前端以"够用即可"的静态 HTML + 原生 JS 实现；后续阶段保留前后端增量扩展空间。

## 2. 系统设计



### 2.1 技术栈


| 层   | 选型                            | 理由                                       |
| --- | ----------------------------- | ---------------------------------------- |
| 数据库 | MongoDB ≥ 6.0                 | 文档模型天然贴合"题型决定字段、答案类型决定值"                 |
| 后端  | FastAPI + Pydantic            | 类型化请求/响应、依赖注入、Swagger UI 自动生成            |
| 鉴权  | JWT (HS256) + bcrypt(cost=12) | 无状态、易扩展                                  |
| 前端  | 纯静态 HTML + 原生 JS              | 零构建、刷新即生效                                |
| 测试  | pytest + FastAPI TestClient   | 与应用共享 fixture，连接隔离用 `config.MONGO_DB` 切换 |




### 2.2 模块划分

```
survey_system/
├── app/
│   ├── main.py            FastAPI 入口，startup 创建索引
│   ├── db.py               MongoDB 连接池（maxPoolSize=50）
│   ├── routing.py         next_rule 解释器（4 种 mode）
│   ├── validation.py      answer 校验解释器（4 种 type）
│   ├── api/               REST 路由（auth/surveys/questions/responses/statistics）
│   └── models/            Repository 层（数据访问 + 一致性校验）
├── frontend/              index.html（管理端 SPA）+ fill.html（公开填写页）
├── tests/                 8 个测试模块，覆盖模型与 API
└── docs/                  数据库设计 + 测试用例
```



### 2.3 API 总览


| 模块         | 端点                                                                         | 说明           |
| ---------- | -------------------------------------------------------------------------- | ------------ |
| auth       | `POST /api/auth/register`、`/login`、`GET /me`                               | 注册/登录/当前用户   |
| surveys    | `POST/GET/PUT/DELETE /api/surveys[/{id}]`、`/publish`、`/close`              | 问卷 CRUD + 发布 |
| questions  | `POST/GET/PUT/DELETE /api/surveys/{id}/questions[/{order}]`                | 题目管理         |
| responses  | `POST /api/surveys/{id}/submit/start`、`/answer`、`/submit`、`GET /responses` | 填写流程         |
| statistics | `GET /api/surveys/{id}/statistics`                                         | 聚合统计         |




### 2.4 关键设计决策

1. **业务规则存数据，不写死代码**：`next_rule` 与 `validation` 都是文档结构，新增跳转模式 / 校验规则不需要改代码路径。
2. **填表前必须登录**：通过 JWT 强制要求 `user_id` 永远非空，匿名性靠 `is_anonymous` 标记而非"不传 user_id"。
3. **统计从原始答案重算**：不在问卷上累加数字，避免数据漂移。
4. **答题路径由后端记录**：`responses.answer_path` 字段由后端在 `routing.resolve()` 调用时写入，便于审计。

## 3. MongoDB 设计

> 详见 `docs/数据库设计.md`。本节摘录关键设计点。



### 3.1 集合划分（5 个独立实体）

```
users ─< surveys ─< questions
            │           │
            └─< responses ─< answers
```


| 集合          | 主要字段                                                                            | 关键约束                                                      |
| ----------- | ------------------------------------------------------------------------------- | --------------------------------------------------------- |
| `users`     | `username`、`password_hash`、`created_at`                                         | `username` 唯一，长度 3-32，规则 `^[A-Za-z0-9_]+$`                |
| `surveys`   | `title`、`owner_id`、`status`、`token`、`allow_anonymous`、`deadline`                | `token` 唯一；状态机 `draft → published → closed`（不可逆）          |
| `questions` | `survey_id`、`order`、`type`、`title`、`options`、`validation`、`next_rule`           | `order` 在同一问卷内唯一；`validation` / `next_rule` 随 `type` 形态不同 |
| `responses` | `survey_id`、`user_id`、`is_anonymous`、`submitted_at`、`answer_path`、`duration_ms` | `user_id` 必填；`is_anonymous` 冗余自问卷                         |
| `answers`   | `response_id`、`question_id`、`value`                                             | `value` 形态随题型变化（单/多/文/数）                                  |




### 3.2 为什么不用关系型数据库


| 维度     | 关系型                       | MongoDB（本项目）               |
| ------ | ------------------------- | -------------------------- |
| 题目字段差异 | 需 EAV 或 JSON 列            | 文档嵌套天然支持                   |
| 跳转规则   | 需额外 `question_branches` 表 | 直接嵌入 `questions.next_rule` |
| 答案类型   | 需拆 3 张表或 JSON 列           | `value` 任意结构，按题型分桶统计       |
| 扩展性    | ALTER TABLE 成本高           | 新增题型友好，第二阶段成本低             |




### 3.3 索引设计（节选）


| 集合          | 索引                                 | 用途      |
| ----------- | ---------------------------------- | ------- |
| `users`     | `{username: 1}` unique             | 注册查重、登录 |
| `surveys`   | `{token: 1}` unique                | 通过短码访问  |
| `questions` | `{survey_id: 1, order: 1}` unique  | 按问卷读题   |
| `responses` | `{survey_id: 1, submitted_at: -1}` | 提交列表    |
| `answers`   | `{question_id: 1}`                 | 单题统计聚合  |

## 4. 跳转设计（`next_rule` 解释器）

> 实现位于 `app/routing.py`。



### 4.1 四种 mode


| `mode`        | 适用题型 | 触发逻辑                                           |
| ------------- | ---- | ---------------------------------------------- |
| `default`     | 任意   | 答完直接走 `fallback`                               |
| `by_option`   | 单选   | 根据选中选项匹配 `branches[].when`，返回对应 `goto`         |
| `by_contains` | 多选   | `when_any`（任一命中）或 `when_all`（全部命中）匹配           |
| `by_range`    | 数字   | 按 `when.op` 与阈值比较（`>=`/`<=`/`>`/`<`/`==`/`!=`） |




### 4.2 关键语义

- `goto` **用题号** `order`**，不用** `_id`：JSON 更易读，与 UI 序号一致。
- `"next"` **/** `"end"` **/** `<order>`：三态返回值，调用方据此决定"顺序下一题"或"结束问卷"。
- **保存时一致性校验**：`QuestionRepo._ensure_no_cycle` 收集所有 `goto` 目标，确保：
  1. 后向 / 越界引用被拒绝；
  2. 前向引用在创建时允许（避免引用尚未创建的题号）；
  3. 不形成环（防呆）。



### 4.5 解耦示例

```json
// Q2 "今天周几" 的跳转规则
{
  "mode": "by_option",
  "fallback": "end",
  "branches": [
    { "when": "周一", "goto": 3 },
    { "when": "周二", "goto": 4 },
    { "when": "周三", "goto": 0 }
  ]
}
```

执行流：用户提交"周二" → `resolve()` 遍历 `branches` 匹配到 `周二→4` → 返回 `4` → API 层把当前题推进到 `order=4`（周二日程）。

## 5. 校验设计（`validation` 解释器）

> 实现位于 `app/validation.py`。



### 5.1 按题型分桶


| 题型       | `validation` 字段                                  | 失败示例                  |
| -------- | ------------------------------------------------ | --------------------- |
| `single` | `required`、`options`                             | 选项不在 `options` 中 → 拒绝 |
| `multi`  | `required`、`min_count`、`max_count`、`exact_count` | 少于 2 个 → 拒绝           |
| `text`   | `required`、`min_len`、`max_len`                   | 长度超限 → 拒绝             |
| `number` | `required`、`min`、`max`、`integer_only`            | 小于最小值 → 拒绝            |




### 5.2 关键设计点

1. **纯函数式**：`validate_answer(type, value, validation, options)` 不依赖任何全局状态，便于单元测试。
2. `options` **从题目文档注入**：避免在重复校验列表。
3. `required` **缺省为** `false`：避免老数据迁移时必填状态冲突。
4. **错误信息携带实际值**：例如 `"number must be ≥ 0; got -1"`，便于前端定位。



### 5.3 双重拦截

- 题目添加 / 更新时：`QuestionRepo.add()` 校验 `validation` 结构合法。
- 答题提交时：`ResponseRepo.record_step()` 实时校验 `value`，不合法返回 400。

## 8. 遇到的问题



### 问题 1：跳转 `goto` 目标校验冲突

- **现象**：早期 `_ensure_goto_targets_exist` 拒绝所有不存在目标（含前向引用），导致 `test_cycle_detection` 失败；同时合理使用下"前向引用合法"被误判。
- **影响**：保存题目时无法引用尚未创建的后续题号；测试频繁出现"该允许的被拒绝"。



### 问题 2：FastAPI 依赖注入与 MongoDB singleton 不兼容

- **现象**：`dependency_overrides` 覆盖 `get_db_handle` 无效，因 `Depends(get_db_handle)` 传入的是 `Database` 对象而非函数。
- **影响**：测试无法做到 DB 隔离，多个测试模块间相互污染。



### 问题 3：FastAPI 0.115.0 对 204 端点返回注解严格限制

- **现象**：`delete_question` 函数带 `-> None` 返回注解时，FastAPI 0.115.0 抛错。
- **影响**：DELETE 请求 500 错误。



### 问题 4：前端 SPA 中 JS 函数被覆盖丢失

- **现象**：`StrReplace` 第二次操作时把 `renderQuestionList` 函数体覆盖为 modal 代码，导致 `Can't find variable: renderQuestionList`。
- **影响**：添加题目按钮报错，整个问卷编辑器不可用。



### 问题 5：MongoDB 高频连接耗尽

- **现象**：连续高频运行 pytest 时出现 `pymongo.errors.AutoReconnect: connection closed` 与 `OperationFailure: Too many open files`。
- **影响**：测试偶发失败，但每次单独运行都通过。



### 问题 6：登录后 `setAuth` 调用顺序导致 401

- **现象**：登录成功后前端在 `/auth/me` 返回后调用 `setAuth`，出现 401 显示"not authenticated"。
- **影响**：用户登录后无法跳转回原目标页。



### 问题 7：未登录态访问 `?token=…` URL

- **现象**：未登录用户访问 `index.html?token=…` 直接进入填写视图，所有 API 401。
- **影响**：用户无法填写通过分享链接得到问卷。



### 问题 8：问卷填写中 token 过期无修复路径

- **现象**：填写中途 token 过期，前端仅显示错误，无修复路径。
- **影响**：用户必须重新获取链接，填写数据丢失。

## 9. 如何解决



### 解决 1：跳转校验拆分为两道关

- 在 `_ensure_no_cycle` 中只检查"后向引用 + 越界"；前向引用允许。
- 移除 `_ensure_goto_targets_exist` 中过于激进的全量检查。
- 调整对应测试用例的 `fallback` 值（`99` → `0`）以匹配语义。



### 解决 2：测试隔离改用 `config.MONGO_DB` 切换

- 放弃 `dependency_overrides` 路线。
- 直接在 `conftest.py` 的 fixture 中临时修改 `config.MONGO_DB`，teardown 恢复。



### 解决 3：删除 204 端点返回注解

- `delete_question` 函数去掉 `-> None` 注解。
- 同步测试断言由 200 改为 204。



### 解决 4：在正确位置重新插入 `renderQuestionList`

- 不再用 `StrReplace` 覆盖；改为定位 `initEditor` 函数末尾插入完整函数体。
- 之后所有改动改用 `replace_all=false` 的精确替换。



### 解决 5：MongoDB 连接池调优

- `pymongo.MongoClient` 初始化参数 `maxPoolSize=50, minPoolSize=1`。
- 根因在 MongoDB 服务端文件描述符限制；课程作业阶段不深究。



### 解决 6 / 7 / 8：填写页面登录与 token 流程重构

- 未登录访问 `index.html?token=…` 或 `fill.html?token=…`：前端检测后立即 `location.href = "/index.html?token=..."` 跳转到登录页，登录成功后再回到填写页。
- 登录成功后 `setAuth` 在 `/auth/me` 之前调用，确保 token 已写入 localStorage。
- 填写中 token 过期：捕获 401 后清空登录态，跳转登录页，提示"会话已过期，请重新登录"。
