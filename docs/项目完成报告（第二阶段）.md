## 1. 本阶段目标

第一阶段交付的问卷系统里，题目只能"长"在问卷里：换个问卷就要重新抄一遍，改题又会牵动历史数据。
用户在《需求变更说明》中提出八条诉求，本阶段的目标是**在不破坏第一阶段全部行为的前提下**，
把"题目"从问卷内部解耦出来，成为可保存、可共享、可版本化、可跨问卷统计的一等公民。

### 1.1 八条需求与落地结果

| 编号 | 需求（用户原话摘要） | 落地形式 | 状态 |
| --- | ---------------------------------------------------------- | ------------------------------------------------------------ | --- |
| 一 | 保存常用题目，以后重复使用 | `POST /api/bank/questions` 新增 `bank_questions` 集合 | ✅ |
| 二 | 把题目分享给同事用 | `POST /api/bank/questions/{id}/share`，支持指定用户名 / 公开 | ✅ |
| 三 | 修改题目不要影响已做好的问卷 | 修改 = 新建版本；问卷侧存**快照** | ✅ |

## 2. 核心设计

### 2.1 三条互相咬合的规则

整个第二阶段可以概括成三条规则，代码里的每一处分支都能对回这三条：

**规则一：题目是版本，不是文档。**
`bank_questions` 里**一个文档 = 一个版本**。同一道题的所有版本用 `root_id` 串成"题目家族"，
用 `parent_id` 记录"这个版本从哪个版本改过来"。改题 = 插入新版本文档，旧版本文档原封不动。
这样"历史版本"不是额外维护的日志表，而是数据模型本身的自然产物——需求四与需求五因此是同一套机制的两种读法。

```text
root_id = R
┌─────────────┬─────────────┬─────────────┐
│ v1          │ v2          │ v3          │
│ _id = R     │ _id = B     │ _id = C     │
│ parent=∅    │ parent=R    │ parent=B    │
└─────────────┴─────────────┴─────────────┘
```

**规则二：问卷里存快照，不存引用。**
从题库选题时，把 `title / type / options / required / validation` **复制一份**写进问卷的 `questions` 文档，
同时写入一个溯源字段 `bank_ref`（`root_id` / `version_id` / `version` / `title_snapshot`）。

```text
题库 v2（后来又改成 v3）
   │
   │  复制快照（内容定格在 v2 的那一刻）
   ▼
问卷 A 的题目 { title:"你的年龄（修订版）", options:[...] }  ← 永远是 v2 的样子
   bank_ref → { root_id: R, version_id: B }
```

于是需求三（改题不影响旧问卷）**不需要任何额外的版本校验逻辑**：
题库和问卷之间根本没有共享的可变对象，题库怎么改都影响不到问卷。
`bank_ref` 只用于"反查"——需求六（被哪些问卷用了）和需求八（跨问卷统计）都靠它。

**规则三：写操作只有拥有者能做。**
`visibility="public"` 或出现在 `shared_with` 里 = 可读（可在自己问卷中使用）；
修改 / 共享 / 加入题库 / 删除 = 仅 `owner_id`。共享给别人的题目，对方还可以 `fork` 一份到自己的题库，
从此刻起两家互不影响。

### 2.2 需求三 → 需求八 的实现链路

```text
        POST /api/surveys/{id}/questions  { bank_question_id }
                        │
                        ▼
        写入 questions 快照 + bank_ref{root_id, version_id}
                        │
        ┌───────────────┴───────────────┐
        ▼                               ▼
 GET /api/bank/questions/{id}/usage   GET /api/bank/questions/{id}/statistics
 按 bank_ref.root_id 反查 questions    按 bank_ref.root_id 聚合 answers
 → 需求六：被哪些问卷用了            → 需求八：所有问卷里的总体分布
```

### 2.3 数据模型

详见 `docs/数据库设计.md` §4.6。要点：

- 新集合 `bank_questions`：`root_id` + `version` 唯一索引；`owner_id` / `shared_with` / `in_bank` 各建索引。
- `questions` 新增可选字段 `bank_ref`，并对 `bank_ref.root_id` / `bank_ref.version_id` 建索引（需求六、八的性能依赖它）。
- 删除是**软删除**（`deleted_at`），且**已被问卷引用的版本禁止删除**——否则问卷里的题目会失去来源。

## 7. 遇到的问题与解决

### 问题 1：如何让"改题不影响旧问卷"而不引入冗余？

最初想在 `questions` 里只存 `version_id`，读取时实时去题库取内容——这样天然一致，
但会让"历史数据可读性"完全依赖题库不被清理，且题库一删就全乱。
最终选择**存快照 + 存溯源**：内容以快照为准（历史稳定），`bank_ref` 只做反查（统计与使用情况）。
代价是题目内容有冗余，收益是历史数据的语义不会随题库演进而漂移。

### 问题 2：同一道题在列表里出现 v1/v2/v3 怎么办？

`GET /api/bank/questions` 如果直接列出所有版本文档，同一题会刷屏。
处理方式：查询后按 `root_id` 去重，只保留**最新版本**（按 `updated_at` 排序后取第一个），
完整版本链交给 `/versions` 端点单独展示。

### 问题 3：已发布问卷里的题库来源题怎么切换版本？

直接改问卷题目在第一阶段就被禁止（已发布问卷不可编辑），保持不变；
草稿态问卷允许传 `bank_version_id` 切换来源版本，此时更新该问卷题目的快照与 `bank_ref`，
只影响这一份问卷，其他用同一题库的问卷保持原样。

### 问题 4：共享名单用用户名还是用户 ID？

API 对外用**用户名**（`usernames: ["student"]`），内部由 `_resolve_usernames()` 解析成用户 ID 存储，
解析不到的用户名直接 422 报错，避免"共享给了一个不存在的用户"这种静默失败。

### 问题 5：新增 27 条用例后，MongoDB 连接耗尽

第一阶段的测试夹具是"每个用例新建一个独立数据库"（`survey_system_test_<ObjectId>`），用完整个 drop。
本阶段用例数翻倍后，本机 mongod（launchd 托管，文件描述符上限 256）开始频繁报 `Too many open files`。
解决方式：把夹具改成**会话级复用**——整个测试会话共用一个临时库，用例之间只清空集合内容，
会话结束时整体 drop。断言未变，只改隔离机制（`tests/conftest.py`、`tests/test_api.py`）。

### 问题 6：加入问卷后题库的"被引用次数"不刷新

"加入问卷"成功后只弹了提示，没有重新拉取题库列表，导致列表里的"被 N 个问卷题目引用"仍是旧值。
修复：在 `frontend/bank.js` 的加入问卷回调里补上 `await renderBank()`。

### 问题 7：切换题库版本后，"来源版本"与"题目内容"错位

在问卷里把来源版本切到 v1 后，角标显示"来自题库 v1"，但题干仍是 v2 的内容——
因为编辑表单把旧题干当作"显式传入值"提交，后端按"显式字段优先"的规则保留了旧内容。
修复：`frontend/bank.js` 缓存版本列表，切换版本时把该版本的题干 / 选项 / 必答回填到表单，
让"切换版本"这件事在界面上是所见即所得的（改完仍可手动微调）。
